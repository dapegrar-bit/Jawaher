# دليل تشغيل «جواهر ميزان» على GitHub وSupabase وRender وRedis

## لماذا هذه البنية؟

```
العميل عبر HTTPS
    ↓
Render Web (Next.js)
    ↓ proxy same-origin /backend/*
Render Private API (NestJS)
    ├── Supabase PostgreSQL (حسابات/فواتير/صلاحيات)
    └── Render Key Value Redis (حماية محاولات الدخول)

GitHub → GitHub Actions (اختبار/بناء) → Render Blueprint (نشر عند التحديث)
```

## 1. إنشاء مستودع GitHub

أنشئي مستودعًا خاصًا `jawaher-mizan`. من مجلد المشروع على الكمبيوتر:

```bash
git init
git branch -M main
git add .
git commit -m "Initial Jawaher Mizan application"
git remote add origin https://github.com/YOUR_USERNAME/jawaher-mizan.git
git push -u origin main
```

لا ترفعي `.env` أو أسرار أو شهادات زاتكا. GitHub Actions ينفذ اختبارات وأوامر بناء API وWeb بعد كل تحديث على الفرع الرئيسي. يسمح Dependabot بطلبات تحديث الاعتمادات.

## 2. إنشاء قاعدة Supabase

- أنشئي مشروعًا جديدًا، واختاري منطقة مناسبة وتحققي من اعتبارات الإقامة النظامية للبيانات.
- افتحي SQL Editor ونفذي `db/ALL_SUPABASE_SQL_EDITOR.sql` لإنشاء جداول التطبيق وحمايتها من طلبات Supabase Data API عبر RLS بلا سياسات للـanon/authenticated.
- من Connect خذي **Session pooler** (IPv4) على المنفذ 5432 إذا لم تتوفر IPv6. لا تفترضي اسم مضيف pooler؛ انسخي السلسلة من لوحة Supabase نفسها.
- تستخدم هذه البنية الاتصال المباشر إلى PostgreSQL من خادم NestJS. لا تستخدم `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` ولا تعرض عنوان قاعدة البيانات ومفتاحها في الواجهة.
- تأكدي من تشفير الاتصالات TLS، واحتياطي البيانات، والتحديثات وسجلات الوصول.
- ملاحظة: RLS دون سياسات يمنع الوصول عن طريق عميل Supabase العام، لكنه ليس بديلًا عن العزل المنطقي للشركات في الخادم. الاتصال بخادم API بصلاحية قاعدة مرتفعة قد يتجاوز RLS. **يلزم مراجعة أمنية مستقلة قبل بيانات حقيقية.**

## 3. النشر على Render

1. Render → New → Blueprint، واربطيه بمستودع GitHub الخاص.
2. يشغّل `render.yaml` ثلاث خدمات: `jawaher-web` عامة، `jawaher-api` خاصة، `jawaher-redis` داخلية.
3. اختاري خطة مدفوعة مناسبة للخدمات الخاصة إذا لزم؛ لا تفترضي أن كل المكونات مجانية.
4. أدخلي `DATABASE_URL` سرًا لخدمة `jawaher-api` في لوحة Render. **لا ترفعي القيمة إلى GitHub**.
5. متغير `REDIS_URL` يُستورد آليًا من خدمة Key Value داخل Render.
6. الواجهة تتصل بخادم API عبر `API_INTERNAL_HOST`، فلا تحتاج عنوان API علني أو صلاحيات CORS عابرة للنطاقات.
7. افحصي رابط `https://YOUR-WEB.onrender.com/backend/health`.
8. راقبي Logs لخدمة API وWeb. لا تستخدمي بيانات إنتاج قبل المراجعة الكاملة.

**الترحيل:** إذا لم تستخدمي محرر SQL، يمكن تشغيل `npm run migrate` من مجلد `api` في بيئة آمنة تمتلك `DATABASE_URL`، بعد نسخة احتياطية. لا تنفذي المسارين معًا دون معرفة سجل الترحيلات.

## 4. دور Redis

- `AuthRateLimiter` يسجّل عدد محاولات الدخول/التسجيل لكل عنوان IP في نافذة 10 دقائق عبر Redis.
- إذا وُجد REDIS_URL وتعذر الاتصال به، يتوقف تسجيل الدخول/التسجيل بدل تجاهل الحماية.
- Redis ليس قاعدة الحسابات؛ القيود والفواتير محفوظة في PostgreSQL.
- يلزم في الإنتاج تفعيل إعدادات proxy الموثوقة وحدود وصول الشبكة، وإجراءات منع الهجمات على API.

## 5. البديل Replit

يحتوي المشروع على `.replit` و`scripts/start-replit.sh` لإطلاق Web وAPI في بيئة تطوير Replit، بشرط إعداد `DATABASE_URL` في Secrets، و`REDIS_URL` إن توفر. نفّذي SQL في Supabase أولًا. هذه تجربة تطوير وليست إثبات صلاحية نشر مالي تجاري.

## 6. ما لا يكتمل تلقائيًا

- لا توجد حسابات Supabase أو Render أو GitHub تم إنشاؤها نيابة عنك.
- لا يوجد اتصال حي بZATCA أو شهادات ومفاتيح إنتاج أو امتثال مُثبت.
- لا توجد صلاحيات أو مفاتيح حقيقية لتكامل Wafeq/Xero.
- لا يوجد اختبار تكاملي مؤكد لـDocker أو للنشر على Render في بيئة إعداد الحزمة.
