# جواهر ميزان — دليل تجهيز التكامل مع زاتكا (ZATCA / FATOORA)
**الإصدار:** 1.1 | **التاريخ:** 20 أكتوبر 2026 | **اللغة:** العربية

> **مهم جدًا:** أضيفت في هذه الحزمة وحدة إعداد وربط للمحاكاة فقط. لم يجرِ اتصال فعلي بالهيئة، ولا يوجد توليد نهائي أو توقيع لفواتير UBL، ولم تحصل أي شهادة رسمية أو موافقة إنتاجية. لا يجوز استخدام المستندات الحالية كفواتير إلكترونية نظامية.

## 1) ما نُفذ بالفعل

1. شاشة داخل برنامج جواهر ميزان: **الامتثال والضريبة**.
2. ملف ضريبي لكل منشأة: الاسم القانوني، رقم تسجيل القيمة المضافة، السجل التجاري (اختياري)، العنوان الوطني، مدينة، حي، شارع، اسم وحدة EGS.
3. تحقق أولي من القيم (ليس تحققًا رسميًا من صحة تسجيل المنشأة لدى الهيئة).
4. تصنيف فواتير مبيعات البرنامج إلى **قياسية Standard** أو **مبسطة Simplified**.
5. تقرير نواقص لكل فاتورة يستعرض بيانات المنشأة والعميل والنوع والحقول المعروفة.
6. مسارات API للمحاكاة **فقط**: التحقق التجريبي `compliance/invoices`، التخليص `invoices/clearance/single` والإبلاغ `invoices/reporting/single`، شريطة تقديم XML موقع ومُتحقق منه مسبقًا خارج هذا المشروع.
7. حماية تشغيلية: المحاكاة معطلة افتراضيًا، بيانات المحاكاة مرتبطة بمعرّف شركة واحد، المالك فقط يستطيع التجريب، لا توجد مسارات إنتاج أو حفظ لشهادات في قاعدة البيانات.
8. سجل محاولات يحفظ حالة الاستجابة ومعرف المستند وبصمة الحمولة دون حفظ XML أو رمز سرّي أو كلمة مرور.
9. اختبارات وحدات وتكامل بعزل الشبكة باستخدام استجابات وهمية فقط.

## 2) ما *لم* ينفذ حتى الآن

- مولد UBL XML نهائي مدقق على قاموس البيانات وكافة قواعد ZATCA.
- توقيع XML الرقمي (XAdES وغيرها من متطلبات الهيئة)، حساب Invoice Hash وPIH مع التسلسل الصحيح، ICV وQR كامل الملحقات.
- إدارة الشهادات/المفاتيح عبر HSM أو KMS وعزلها ومداورة صلاحيتها.
- عملية CSR، الحصول على Compliance CSID، اختبارات جميع أنواع المستندات، ثم الحصول على Production CSID؛ التنفيذ الحالي يتوقع استكمالها بواسطة SDK وأدوات مزود متخصص.
- التحقق المستقل والآلي بواسطة SDK الرسمي من كل XML قبل الإرسال.
- فواتير الإشعار الدائن والمدين، المرتجعات، الخصومات والأسباب الضريبية الاستثنائية.
- التخليص/الإبلاغ الإنتاجي، آلية إعادة المحاولة المضمونة، مهل الإرسال، استقرار معالجة الأخطاء، مراقبة الإنتاج، وإقفال تسلسل مستندات ZATCA.
- اختبار اتصال حقيقي ببيئة محاكاة ZATCA أو اعتماد حل إنتاجي.

## 3) تشغيل قاعدة بيانات جديدة

بعد تنزيل ZIP وفك الضغط انسخي `.env.example` إلى `.env` وغيري كلمة مرور PostgreSQL الافتراضية، ثم:

```bash
docker compose up --build -d
```

PostgreSQL سينشئ على قاعدة **جديدة فقط** الجداول من `001_init.sql` و`002_commerce.sql` و`003_zatca_preparation.sql` بالترتيب. **إذا كانت لديك بيانات قديمة** احفظي نسخة احتياطية ثم نفذي الترقية على بيئة اختبار أولًا:

```bash
# عند وجود حاويات ومجلد المشروع:
docker compose exec -T db psql -U jawaher -d jawaher_mizan < db/003_zatca_preparation.sql
```

لا تستخدمي `docker compose down -v` على قاعدة فيها بيانات؛ هذا يحذف وحدة التخزين الافتراضية.

## 4) تهيئة الحساب داخل جواهر

- افتحي `http://localhost:3000` في جهاز التطوير.
- سجلي الدخول بصلاحية **مالك المنشأة**.
- افتحي تبويب **الامتثال والضريبة**.
- أدخلي **بيانات المنشأة الرسمية**؛ لا تستخدمي بيانات وهمية لاختبار ZATCA الحقيقي.
- افتحي فاتورة مبيعات داخلية وحددي نوعها: Standard أو Simplified ثم شغّلي الفحص المبدئي.
- راجعي الملاحظات؛ ظهور نقص تقني دائم (التوقيع وSDK) أمر مقصود وليس عطلًا.

## 5) التفعيل الاختياري للمحاكاة (غير الإنتاج)

**قبل التفعيل:** احصلي من بوابة فاتورة *المحاكاة* على بيانات الربط التجريبية لشركة واحدة، واستكملي إنشاء CSR وCompliance CSID والتحقق وPCSID باعتماد أدوات الهيئة الرسمية؛ لا تستخدمي بيانات الإنتاج. لا تضعي OTP أو مفتاحًا خاصًا في المحادثات أو الكود أو HTML أو المستودع.

احتفظي بقيم التجربة في مدير أسرار، أو مؤقتًا في `.env` محلي غير مشارك:

```dotenv
ZATCA_SIM_ENABLED=true
ZATCA_SIM_COMPANY_ID=<UUID of company in Jawaher>
ZATCA_SIM_BINARY_SECURITY_TOKEN=<simulation binarySecurityToken>
ZATCA_SIM_SECRET=<simulation secret>
```

أعيدي تشغيل حاوية API بعد تغيير الإعدادات. التشغيل غير مفعل إذا كانت أي قيمة ناقصة أو لم يطابق معرّف الشركة. **لا يتضمن هذا الإصدار أي مفتاح يؤدي إلى الإنتاج**، ولا يجوز نسخ بيانات أو شهادات الإنتاج إلى حقول المحاكاة.

تُثبّت قيمة الوجهة في الكود على:
`https://gw-fatoora.zatca.gov.sa/e-invoicing/simulation`

المسارات المنفذة في الكود لا تقبل عنوان URL خارجيًا يقدمه العميل. ولم تُضف مسارات استدعاء الإنتاج عمدًا.

## 6) تسلسل الربط النظامي المطلوب

1. التسجيل الملائم في بوابة فاتورة للمنشأة بعد التحقق من أهلية الإلزام، وتحديد وحدات EGS.
2. إنشاء زوج مفاتيح وشهادة طلب CSR وفق إعداد البيئة (المحاكاة تختلف عن الإنتاج).
3. الحصول على OTP من البوابة؛ راجعي مدة صلاحيته المعمول بها (يوضح دليل الهيئة ساعة واحدة عند إصداره).
4. طلب **Compliance CSID** باستخدام CSR وOTP.
5. توليد عينات UBL 2.1 صالحة وموقّعة حسب أنواع الفواتير والإشعارات، وإجراء اختبارات **Compliance** المطلوبة لدى الهيئة وSDK.
6. طلب شهادة **PCSID** الخاصة بالبيئة المختارة.
7. إرسال اختبار فاتورة قياسية عبر **Clearance**، وفاتورة مبسطة عبر **Reporting**، والتعامل مع الرفض والتحذيرات والتوقيع والتسلسل.
8. إجراء اختبارات تكامل وأمن واستعادة وسجلات، وتوثيق جميع نتائج ZATCA SDK.
9. بعد النجاح والمراجعة، تخطيط ربط **الإنتاج** مع بوابة المنشأة الحقيقية في إصدار لاحق مع فصل البيئة وإدارة مفاتيح خاصة بكل EGS.

## 7) API الجاهزة في جواهر

| Method | Route | الوظيفة |
|---|---|---|
| GET | `/companies/:cid/zatca/status` | حالة الملف وجاهزية المحاكاة |
| POST | `/companies/:cid/zatca/profile` | تحديث ملف المنشأة (المالك) |
| GET | `/companies/:cid/zatca/documents` | فواتير المبيعات ذات الصلة |
| POST | `/companies/:cid/zatca/documents/:id/category` | اختيار standard أو simplified |
| GET | `/companies/:cid/zatca/documents/:id/preflight` | فحص النواقص |
| GET | `/companies/:cid/zatca/simulation/history` | آخر محاولات المحاكاة |
| POST | `/companies/:cid/zatca/documents/:id/simulation/:operation` | إرسال XML خارجي موقع إلى المحاكاة (مقفل افتراضيًا) |

`operation` من `clearance` أو `reporting` أو `complianceInvoices` فقط. المتطلب `confirmedSdkValidation` إقرار المطور بنتيجة فحص SDK وليس اختبارًا مستقلًا من نظام جواهر.

**مثال جسم طلب محاكاة (قيم توضيحية غير صالحة للإرسال):**

```json
{
  "confirmedSdkValidation": true,
  "envelope": {
    "invoiceHash": "<sha256-base64-from-official-SDK>",
    "uuid": "<uuid-of-signed-invoice>",
    "invoice": "<base64-of-complete-signed-ubl-xml>"
  }
}
```

لا ترسلي XML بدون توقيع إلى ZATCA. هذه البنية فقط هي الغلاف المتوقع من API؛ جميع محتوياته الحقيقية يجب أن تنتج من عملية توقيع وتحقق مستقلة مكتملة.

## 8) معايير قبول قبل أي إنتاج

| المسار | معيار القبول | الوضع الآن |
|---|---|---|
| الملف الضريبي | بيانات منشأة حقيقية ومتحقق منها | فحص شكلي فقط |
| XML UBL | ينجح XSD وSchematron وقواعد ZATCA | غير منجز |
| التوقيع | تجزئة وتوقيع صحيحان لكل نوع وفترة | غير منجز |
| شهادة CSID | مرخصة وصالحة للمنشأة ووحدة EGS | غير منجز |
| التجربة | نتائج استجابات حقيقية موثقة | لم تختبر |
| الفاتورة القياسية | Clearance قبل التسليم حسب المتطلبات | غير منجز |
| الفاتورة المبسطة | Reporting ضمن المهل المطلوبة | غير منجز |
| الإشعارات | credit/debit notes كاملة | غير منجز |
| أمان الإنتاج | إدارة مفاتيح وتدقيق واختبار اختراق | غير منجز |
| استمرارية التشغيل | معالجة انقطاع اتصال دون فقد أو ازدواج | غير منجز |

## 9) ملاحظات تنظيمية مهمة
